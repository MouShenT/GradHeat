# GradHeat 设计方案

> 11408 考研院校专业热度评估与择校分析平台
> 版本 v0.1 · 2026-09-18

---

## 〇、先明确一件事：这个项目真正难的地方

不是爬虫，不是后端，不是前端。

**难在「数据完整性」** —— 11408（政治 + 英一 + 数一 + 408）是考研最卷的赛道之一，但：

- 各校「报考人数」公布率不到 20%
- 「报录比」大量学校根本不公开
- 同一指标各校口径不一致（含不含推免？含不含非全？含不含调剂？）
- 大量数据只存在于考研机构的付费渠道里

**所以这个项目的设计原则是：承认数据缺失，用可量化的方式表达可信度，而不是假装数据完整。**

任何声称「我们有全国所有学校的报录比」的方案，要么在造假，要么在侵权。

---

## 一、维度选择（这是最关键的设计）

### 1.1 三层维度框架

我把评估维度分成三层，按「可信度从高到低、信息量从低到高」排列：

#### 第一层：官方硬数据（可信度 ★★★★★）

来源：院校研究生院官网、研招网

| 维度 | 说明 | 数据可得性 |
|------|------|-----------|
| 招生计划数 | 统考名额（需剔除推免） | 高（招简必发） |
| 实际录取数 | 拟录取名单计数 | 高（名单必公示） |
| 复试分数线 | 院线/校线 | 高 |
| 复试名单人数 | 进入复试的人数 | 中 |
| 复试差额比例 | 复录比 = 复试人数/录取人数 | 中 |
| **录取考生分数分布** | 均分、中位数、最低分、各分位数 | 高（从拟录取名单反推） |

> **「录取均分」是整个项目最有价值的单一指标。** 因为它客观、可比、能反推真实竞争强度。一个学校如果录取均分 370，它不需要公布报录比，热度也一目了然。

#### 第二层：热度代理指标（可信度 ★★★☆☆）

来源：搜索引擎、内容平台。这些是**行为数据**，反映的是关注度，不是报考难度。

| 维度 | 采集源 | 说明 |
|------|--------|------|
| 搜索指数 | 百度指数 | 校名+专业关键词趋势 |
| 讨论量 | 知乎、B站、贴吧 | 提及量与增量 |
| 内容供给 | B站/公众号相关视频文章数 | 反映机构与考生的关注密度 |
| 报考人数 | 研招网（部分省份公布） | 最直接但覆盖率低 |

> **代理指标的核心价值不是替代报录比，而是捕捉变化趋势。** 一个学校突然被自媒体推火，搜索量会先于录取分数线体现出来 —— 这是预警信号。

> **工程约束（调研结论）：本层的每个信号源都必须可插拔、可降级。**
> 百度指数需要登录 Cookie + 加密参数逆向，逆算法随时可能失效；知乎/B站的反爬也在变化。
> 因此：单一信号源失效时系统必须降级运行并明确标注「该维度数据缺失」，而不是抛异常或填假数据。
> 详见 [PRIOR-ART.md](PRIOR-ART.md) §2.2。

#### 第三层：竞争激烈度（可信度 ★★★★☆）

由第一层数据派生，是人算出来的而不是抓来的：

| 指标 | 计算方式 |
|------|---------|
| 录取均分 | 拟录取名单分数的算术平均 |
| 分数分位数 | P25 / P50 / P75 / P90 |
| 高分段占比 | 370+ 考生占比 |
| 复录压力 | 复试人数 / 录取人数 |
| 推免挤压度 | 推免数 / 总计划数 |
| 分数年际波动 | 近 3 年均分标准差 |

### 1.2 为什么这样分层

用三个具体场景说明：

**场景 A：某校不公布报录比，但公布拟录取名单**
→ 从名单反推均分和分位数 → 竞争激烈度层给出可靠结论
→ 不需要报录比也能判断热度

**场景 B：某校今年突然被某机构推火**
→ 搜索指数和讨论量暴增 → 代理指标层捕捉异常
→ 但录取均分要明年才体现 → 用代理指标做**前瞻预警**

**场景 C：两个学校热度看起来一样**
→ 拆开看：一个均分 350/复录比 1.2，另一个均分 350/复录比 1.8
→ 复录压力不同 → 竞争激烈度层区分出真实的报考难度差异

### 1.3 第一期院校选取原则（10~20 所）

不要随机选，按「代表性」选，保证每个维度都能被验证：

1. **数据全公开型**（如部分 985/211）：用来验证全链路
2. **数据半公开型**：只有拟录取名单，没有报录比 —— 验证反推逻辑
3. **数据稀缺型**：只有招简 —— 验证代理指标的兜底能力
4. **地域覆盖**：北上广 / 中部 / 西部各选，避免地域偏差

### 1.4 变更监听（这是「监听」需求的正确形态）

曾考虑「像流量监听一样监控报名按钮点击 / 页面访问量」。**结论：流量监听不可行，变更监听可行且价值更高。**

**为什么流量监听不可行**：

| 想要的信号 | 为什么拿不到 |
|-----------|------------|
| 报考人数（点击报名按钮的人） | 是**服务端数据**，只存在于研招网内部；只有它主动公布才有（部分省份公布，覆盖率低） |
| 考研网页的访问量 | `.edu.cn` 站点**不装第三方统计**，无任何公开计数器 |
| 第三方估算（SimilarWeb / 站长工具 / 爱站） | 只到**整站域名级**，且对中国 `.edu.cn` 的估算基本是噪声 —— 不能用来比两所学校的专业热度 |

> 任何声称能给出「某校某专业报名人数」的第三方，都只能靠估算或推测，达不到我们机制 1 的来源分级要求。**宁可没有，不要假数据。**

**可行的替代 —— 变更监听（Change Detection）**：定时抓取目标页面，比对内容 hash / DOM diff，**变更即触发管道**。它不是流量指标，而是**数据管道的输入端 + 结构变化告警**：

| 监听对象 | 变更意味着 | 情报价值 |
|---------|-----------|---------|
| **招生简章 / 专业目录** | 发布、修订 | 触发采集；捕捉**缩招、改考（如 408 改自命题）、学制变化** |
| **拟录取名单** | 公示 | 触发采集；这是录取均分的数据源 |
| **复试分数线 / 复试名单** | 公布 | 触发采集 |
| **调剂公告 / 调剂系统名额** | 开放、名额变动 | 见下方「调剂抢空速度」 |
| **报名情况 / 报名人数播报** | 报名期发布 | ⭐ 唯一能在报名期拿到的真实报考数据 → 见 §1.5（报名期专项高频任务） |
| **页面结构本身** | 改版 | ⚠️ **解析器失效的早期预警** —— 改版当天就知道，而不是等到抓出 0 条（见 DESIGN.md §机制 9 ①） |

**额外发现的一个强信号 —— 「调剂抢空速度」**：

调剂系统开放时，名额是**公开可见且实时减少**的。从「名额 N」到「名额 0」的**时长**，是一个**公开可观测、无法伪装的真实需求信号**：越是抢手的学校/专业，名额消失越快。

- 优点：真实行为数据、公开可见、不依赖任何第三方估算
- 缺点：**需要每天多次高频监测**（否则只能得到一个区间），且只在调剂季（3–4 月）可用
- 定位：**高价值但低频的补充信号**，不进第一期，列入 Phase 2 候选（需先在调剂季实测可行性）

**工程载体**：[changedetection.io](https://github.com/dgtlmoon/changedetection.io)（34,319★）开箱即用，但它是「变更 → 给人发通知」的监控台；**我们的需求是「变更 → 触发入库管道」**，自建 httpx + hash + diff 更贴合且可控。**倾向自建**，详见 [PRIOR-ART.md](PRIOR-ART.md) §7.5。

### 1.5 报名期进度快照（唯一能在报名期拿到的真实报考数据）

**先说清楚什么拿不到**（已核实，2026-09-18）：

| 想要的 | 结论 | 原因 |
|--------|------|------|
| 研招网站点流量 | ❌ 不可得 | 无公开计数器；第三方只到 `chsi.com.cn` 域名级 |
| 各校报名人数实时分布 | ❌ 不可得 | 网报系统是**登录态、每人只看得见自己填的那份**；研招网不提供任何实时报考人数查询 |
| 研招网页面「关注人数/热度」 | ❌ 不存在 | 已核实官方硕士专业目录只有招生人数、导师、考试科目等硬信息，无热度字段 |

> **这不是技术问题，是制度设计。** 若考生能实时看到各校报名人数，会立刻引发扎堆/规避的博弈，报名秩序会被打乱。教育部刻意不公开 —— **不要试图绕过，也不要接受任何第三方的估算值。**
>
> 由此推导出一条排除规则：**不用「准考证号推算」等民间估算方法** —— 精度不达标，过不了来源分级。

**但有一个真正的增量：部分学校在报名期间主动公布报名进度。**

实测案例（均为**报名窗口未关**时发布）：

| 学校 | 公布时点 | 数据 |
|------|---------|------|
| 北京航空航天大学 | 2024-10-23 | 12,714 人，同比 **-7%**，连续第三年下降 |
| 沈阳药科大学 | 2024-10-23 | 3,196 人，同比 **-31%** |
| 西安财经大学 | 2024-10-28 | 4,691 人，同比 **-25%** |

**→ 落地为「报名期进度快照」维度**：

| 项 | 设计 |
|----|------|
| 来源分级 | **L1**（招生单位官方发布） |
| 采集方式 | **报名期（10 月）专项变更监听任务**，逐日扫目标院校研招网「报名情况」栏目 |
| 复用 | 直接复用 §1.4 的变更监听基础设施 —— **一个设施，两个用途** |
| 存储形态 | **时间序列快照**，不是单值（见下方硬性规则） |
| 覆盖率 | **低**（自愿公布，永远是少数） → 未公布即 `missing` |

**硬性规则**：

1. **未公布 = `missing`，不用代理指标补估算值** —— 否则会混入「某校是官方数据、某校是估算」的不可比数据
2. **两个时间必须分开记录**：`published_at`（学校公布的时点）与 `observed_at`（我们观测到的时点）。我们第 8 天才发现学校第 5 天发的公告，这两个时间不一样
3. **快照之间的差值 > 单点绝对值** —— 同一学校多次播报时，增量才是真信号
4. **跨校比较必须对齐时点** —— 不能拿 A 校第 3 天的数据比 B 校第 10 天的数据
5. **保存学校原文，不保存加工后的百分比** —— 「同比下降 31%」对比的是去年哪个时点？口径不明（机制 5）
6. **必须标注「未经网上确认」** —— 报名期是滚动值，会含取消报名、重复报名、网上确认不通过者。最终有效人数要等 11 月网上确认之后

> ⚠️ **解读纪律：不能用「学校是否公布」作为热度指标。** 那测的是学校的宣传意愿，不是热度 —— 北大从不公布，不代表北大冷。公布行为本身带动机（有的公布低数字吸引考生，有的公布高数字劝退），解读时须过机制 8 的反方审查。

**配套的宏观背景数据**（只做归一基准，不做院校排名）：

- **省级报名总数**：山东 35.5 万 / 江苏 25.2 万 / 广东 21.26 万 …（各省考试院）
- **全国报名总数**：2025 年 388 万，同比 **-11.4%**（教育部）
- **报考点爆满时序**：各省考试院发布「已满报考点实时更新公告」，部分考点会临时扩容（3,000 → 3,500）

> ⚠️ **报考点选的是「在哪考」，不是「考哪个学校」。** 它反映的是该省/该市的考研总量热度，**不能拆分到学校**。且「某考点满了」可能是容量小而非热度高 —— 要结合**满的速度**与**是否扩容**一起看。

## 二、技术选型

### 2.1 前端：Vue 3（推荐，理由具体）

| 候选 | 结论 | 理由 |
|------|------|------|
| **Vue 3 + TS** | ✅ 选它 | 生态完整，ECharts 集成成熟；组合式 API 适合图表密集场景；中文社区资料最多 |
| React | 备选 | 生态更强但图表密集场景下状态管理更啰嗦 |
| Svelte | ❌ | 生态小，遇到问题不好查 |

具体栈：

```
Vue 3 + TypeScript + Vite
- UI:      Element Plus（表格/筛选/表单场景最省事）
- 图表:    ECharts 5（热度趋势、分数分布、院校对比，全部靠它）
- 状态:    Pinia
- 路由:    Vue Router
- 请求:    Axios + 统一封装
```

### 2.2 后端：Spring Boot 3 / Java 17

```
Spring Boot 3.x + Java 17
- 持久层:  MyBatis-Plus（中文生态，CRUD 快）
- 缓存:    Spring Data Redis
- 消息:    Spring AMQP (RabbitMQ)
- 文档:    SpringDoc OpenAPI（自动生成接口文档）
- 认证:    Spring Security + JWT（如果要开放注册）
```

### 2.3 消息队列：**选 RabbitMQ**

| 候选 | 结论 | 理由 |
|------|------|------|
| **RabbitMQ** | ✅ 选它 | ① 轻量，单机 Docker 一行起 ② 灵活路由（爬虫任务分发 / 结果回流 / 优先级队列都支持）③ 管理 UI 可视化，调试爬虫任务流非常省事 ④ 你 VM 上已有同款经验 |
| Kafka | ❌ 现阶段过重 | 高吞吐日志场景才需要；运维成本高（ZK/KRaft）；这个项目的数据量级（万级/天）用不上 |
| RocketMQ | ❌ | 优势在事务消息和超大吞吐，中小项目引入代价不划算 |

**最终答案：RabbitMQ。** 规模不对的时候，轻量可控比高性能重要。

### 2.4 爬虫：Python

```
Scrapy        静态页面批量抓取（招简、名单列表页）
Playwright    动态渲染页面（研招网等 JS 站点）
Celery        + RabbitMQ 做定时调度与任务分发
Pydantic      数据校验与清洗
```

### 2.5 基础设施（已完成部署）

```
VM: ms@192.168.43.150
├── MySQL 8.0      容器 gradheat-mysql      库 gradheat
├── Redis 7        容器 gradheat-redis      缓存 + 去重
└── RabbitMQ 3.13  容器 gradheat-rabbitmq   vhost /gradheat
```

详见 `infra/docker/README.md`。

**出网决策（2026-09-18 确认）**：**Docker 容器不配代理**，容器只跑存储/中间件（MySQL / Redis / RabbitMQ），全部是内网服务，不需要出网。

需要访问境外站点（SearXNG 抓 Google/Bing 等）的采集任务，**直接跑在 Kali 宿主机上**，复用宿主机已有的 mihomo（`127.0.0.1:7890`，`mode: rule`）。这样：

- 不需要改 mihomo 的 `allow-lan`（不碰 VM 上其他项目在用的配置）
- 不需要 `network_mode: host`（不破坏容器的端口隔离约定）
- 采集进程与宿主机代理处于同一网络命名空间，`127.0.0.1:7890` 直接可达

⚠️ **但必须注意代理的边界**（详见 §风险与对策 与 PRIOR-ART.md §7.4）：宿主机 shell 里已设 `HTTP_PROXY/HTTPS_PROXY` 环境变量，而 `NO_PROXY` **只覆盖内网网段，不含 `.cn`/`.edu.cn`**。因此抓国内院校官网时不能无脑继承环境变量 —— 应显式控制请求的代理策略（国内直连、境外走代理），并在启动时验证出口 IP。

## 三、总体架构

```
                    ┌─────────────────────────────────────┐
                    │        数据源                        │
                    │  研招网 / 院校官网 / 百度指数 / UGC   │
                    └──────────────┬──────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
                    │   Python 爬虫层                      │
                    │   Scrapy + Playwright                │
                    │   · 定时任务（Celery Beat）           │
                    │   · 反爬策略（限速/UA轮换/代理池）     │
                    └──────────────┬──────────────────────┘
                                   │ 原始数据 + 证据 URL
                    ┌──────────────▼──────────────────────┐
                    │   RabbitMQ                           │
                    │   queue: crawl.raw                   │
                    │   queue: crawl.retry                 │

                    ┌──────────────▼──────────────────────┐
                    │   Spring Boot 服务层                  │
                    │   · 消费爬虫数据 → 解析 → 校验 → 入库  │
                    │   · 指标计算（均分/分位/热度分）        │
                    │   · REST API                          │
                    └──────┬───────────────────┬──────────┘
                           │                   │
              ┌────────────▼──────┐   ┌────────▼─────────┐
              │  MySQL            │   │  Redis           │

              [后期] Python 智能体服务 ── 择校推荐 / 问答
```

**数据流向一句话**：爬虫抓 → MQ 缓冲 → Spring Boot 消费入库 → 定时算指标 → 前端展示。

**为什么爬虫和消费解耦**：爬虫会失败、会被封、会重试，MQ 让抓取和处理互不阻塞。爬虫挂了不影响已有数据处理，后端重启不丢爬虫产出。

## 四、数据模型（核心表）

```sql
-- 院校
school(id, name, province, city, level_tags, is_985, is_211, is_dfc)

-- 招生单位（学院/系）
department(id, school_id, name, code)

-- 专业（11408 = 计算机相关学硕/专硕）
major(id, department_id, name, code, exam_type, is_11408)

-- 年度招生数据（第一层硬数据）
admission(
  id, major_id, year,
  study_mode,          -- 全日制/非全 ★口径关键，逐年份记录
  degree_type,         -- 学硕/专硕 ★口径关键，逐年份记录
  national_line,       -- 国家线 ★判断「分数洼地」的基准
  plan_total,          -- 总计划
  plan_recommend,      -- 推免数
  plan_exam,           -- 统考名额
  applied_count,       -- 报考人数（可能为空）
  admitted_count,      -- 录取人数
  retest_count,        -- 复试人数
  retest_line,         -- 复试线
  score_min,           -- 录取最低分
  score_avg,           -- 录取均分
  score_median,        -- 中位数
  score_p25, score_p75, score_p90,
  subject_change,      -- 改考/专业拆并等结构变化 ★
  source_url,          -- 数据来源 URL ★
  source_level,        -- 来源分级 ★
  confidence,          -- 置信度 0~1 ★
  collected_at
)

-- 字段规则（硬性）
-- ① 缺失留空（NULL），不要填 0。0 只表示「官方明确为零」。
-- ② study_mode / degree_type 必须逐年份记录，不能挂在 major 上当作稳定属性：
--    同一专业可能某年新增非全、或学硕改专硕，挂错会产生错误结论。
-- ③ 口径不一致的数据宁可不合并：不同学院 / 专业代码 / 培养方式不得混算。

-- 录取名单明细（用于反推分数分布）
admission_detail(id, admission_id, masked_name, score_total, score_politics,
                 score_english, score_math, score_408, is_recommend, is_adjust)

-- 热度代理指标（时间序列）
heat_signal(
  id, major_id, signal_type,   -- baidu_index / zhihu_count / bilibili_count
  value, stat_date, source_url, source_level, confidence
)

-- 计算后的热度分数（按版本存储，便于回溯算法变更）
heat_score(
  id, major_id, period, score_version,
  dim_official,        -- 官方硬数据分项
  dim_competition,     -- 竞争激烈度分项
  dim_attention,       -- 关注度分项
  total_score,
  confidence,          -- 综合置信度
  computed_at
)

-- 数据来源登记（审计溯源）
data_source(
  id, domain, name, level,      -- 1~4 级
  robots_ok, crawl_interval_sec, note
)

-- 报名期进度快照（§1.5）：时间序列，不是单值
application_snapshot(
  id, school_id, year,
  published_at,        -- 学校公布的时点 ★
  observed_at,         -- 我们观测到的时点 ★ 两者必须分开
  applied_count,       -- 截至该时点的报名人数
  yoy_text,            -- ★ 学校原文的同比表述，不存加工值
  confirmed_online,    -- 是否已过网上确认（报名期必为 false）
  source_url, source_level, confidence, collected_at
)
```

**关键设计：每一条数据都带 `source_url + source_level + confidence`。** 这是「真实性」要求落地的方式 —— 任何一条展示给用户的数据都能追溯到来源，并且知道自己有多可信。

## 五、如何保证「热度和报考的合理性、真实性」

这是你问题里最重要的一条。我拆成 5 个机制：

### 机制 1：来源分级（Data Provenance）

| 级别 | 来源类型 | 举例 | 置信度权重 |
|------|---------|------|-----------|
| L1 | 官方一手 | 院校官网招简、拟录取名单 PDF | 1.0 |
| L2 | 官方二手 | 研招网汇总、省考试院 | 0.9 |
| L3 | 权威第三方 | 教育在线、学校官方公众号 | 0.7 |
| L4 | UGC | 知乎、贴吧、B站 | 0.4（仅做趋势，不做绝对值） |

**规则：不同级别的数据不能直接混算。** 计算指标时必须按级别加权，且 L4 只能用于趋势分析。

**与外部 A/B/C/D 分级的映射**（调研发现已有同类项目用 A–D 四级，见 [PRIOR-ART.md](PRIOR-ART.md) §2.1，这里建立对照，便于将来互相导入数据）：

| 我们 | 外部 | 含义 |
|------|------|------|
| L1 | A | 官方一手（官网招简、拟录取名单原文） |
| L2 | B | 官方二手（研招网汇总、省考试院） |
| L3 | C | 权威第三方（教育在线、官方公众号） |
| L4 | D | UGC（知乎、贴吧、B站） |

### 机制 2：证据留存

- 每次抓取保存**原始 HTML/PDF 快照**（VM 本地 + 定期归档）
- `admission.source_url` 精确到具体文件
- 关键结论（如「2025 年均分 372」）能点开看原始名单

> 这不仅是技术问题，也是合规问题：**我们引用事实，不复制内容。**

### 机制 3：交叉验证

同一个指标如果多个来源都有：
- 一致 → 提升置信度
- 冲突 → 记录冲突，取高等级来源，并在 API 里标注 `disputed: true`
- 只有低等级来源 → 标注「仅供参考」并降低置信度

### 机制 4：时间衰减

热度信号不是恒定的：
```
weight(t) = exp(-λ × Δt)
```
- 报考数据：按届衰减（去年的数据参考价值低于前年？取决于大小年）
- 搜索指数：近 30 天权重大，历史数据参考趋势
- **区分「结构性热度」和「短期噪声」**：短期暴涨（如某校爆出负面新闻）要标注为异常，不直接计入热度分

### 机制 5：口径归一

最容易出错的地方 —— 每个学校的统计口径不同：

| 口径问题 | 处理方式 |
|---------|---------|
| 是否含推免 | 统一拆出 `plan_recommend`，统考口径单独算 |
| 是否含非全 | 用 `admission.study_mode` 标记，默认只看全日制 |
| 是否含专硕/学硕混淆 | 用 `admission.degree_type` 标记，不跨类型合并 |
| 是否含调剂 | `admission_detail.is_adjust` 标记，默认只看一志愿 |
| 分数是初试还是总分 | 统一记录初试总分 |
| 专业代码变更 | 维护专业沿革映射表 |
| 改考/专业拆并 | 用 `admission.subject_change` 记录，作为「结构变化」风险信号 |

**口径不统一的数据比没有数据更危险** —— 因为它会产生错误的结论。

### 机制 6（产品层面）：透明展示

前端不做「一个数字定生死」。每个院校卡片展示：

```
北京邮电大学 · 计算机科学与技术（11408）
热度 87.3  ▓▓▓▓▓▓▓▓▓░
├─ 官方数据完整度: 92%   ✓ 可验证
├─ 录取均分: 372 (P50: 371)  [来源: 2025 拟录取名单 ↗]
├─ 复录比: 1.5 : 1
├─ 关注度: 较去年同期 +23%  (百度指数 + 知乎)
└─ 置信度: 高  (L1 来源 4 项, L3 来源 2 项)
```

**让用户看到「不确定性的边界」，而不是一个假装精确的数字。**

### 机制 7：不确定性量化（不能只靠感觉）

置信度不能拍脑袋给，要有可复算的公式。核心字段覆盖率的算法：

```
coverage = 已有核心字段数 / 应有核心字段数

核心字段 = 近 3 年 × 4 类 = 12 个单元
  ① 复试线   ② 统考名额   ③ 录取分数分布   ④ 竞争数据（复试人数/录取人数）

coverage ≥ 0.75        → 高置信度
0.45 ≤ coverage < 0.75 → 中置信度
coverage < 0.45        → 低置信度
```

**附加约束**：即使 coverage 很高，也只有当**来源 ≥ 2 个且均为 L1/L2**、且不存在未解决的对象混用时，才允许给「高置信度」。单一来源即使字段全，也不给高置信度 —— 因为无法交叉验证。

> 算法来源：同类项目实践，见 [PRIOR-ART.md](PRIOR-ART.md) §2.1。选它的理由是公式简单、可解释、可复算，符合「不做黑盒」的既定原则。

### 机制 8：反方审查与留出检查（防止自我说服）

分析产出高风险结论时，**必须**回答以下 4 问，答不上来就不能下结论：

1. 这个变化**是否由口径变化造成**，而不是竞争真的加剧？
2. 是否存在**缓释证据**（扩招、推免未满、复试保护一志愿）？
3. 最近一年是否为**异常值**（疫情、政策变动、考试难度突变）？
4. 结论在**删除最极端一年**后是否仍然成立？

**留出检查（防自欺）**：如果某校有 4 年以上数据，用早期年份形成判断规则，再看最近一年能否被解释。**禁止事后修改阈值来冒充「预测准确」** —— 那是数据挖掘偏差，不是预测能力。

**结论措辞纪律**：只用「风险 / 情景 / 信号 / 置信度」。禁用「一定爆」「稳上」「准确率 X%」。

**「数据不足」不等于「安全」。** 没有数据支撑的学校不参与排名，也不给低风险标签 —— 缺失是未知，不是利好。

### 机制 9：采集链路的工程纪律（从同类项目的 issue 里学来的）

调研同类项目时读了它们的 **issue / PR**（见 [PRIOR-ART.md](PRIOR-ART.md) §八），发现失效模式高度集中。以下每条都由真实 issue 佐证，**不是理论担忧**：

| 规则 | 说明 | 反面案例 |
|------|------|----------|
| **① 抓到 0 条必须告警，绝不入库为 0** | 0 条通常是「接口变了 / 未登录 / 被限流」，不是「真的没有讨论」 | last30days #11：小红书接口废弃后仍报成功，返回 0 条 |
| **② 入库必带 `fetched_count` 元数据** | 记录「这次抓了几条」，供后续比对 | 无元数据就无法区分「真的少」和「抓挂了」 |
| **③ 条数须与历史基线比对** | 断崖式下跌（如环比 -80%）触发人工复核 | 同上 |
| **④ 健康检查必须发真实请求并校验响应结构** | 只检查「命令存在 / 进程在跑」会给出虚假的健康 | Agent-Reach 的 `doctor` 自检误报 |
| **⑤ 健康状态分三态：healthy / degraded / down** | 「能跑但降级」（如切换到了备用后端、爬到的是缓存）必须单独标出 | 静默降级比直接失败更危险 |
| **⑥ 凭据失效必须显式降级，不得静默回退** | 账号 Cookie 过期 → 标记指标为 `missing`，并在前端显示「该指标本期不可用」 | 静默回退会污染趋势线 |
| **⑦ 解析器对平台改版零容忍** | 关键 selector / 字段缺失即整条丢弃并告警，不「尽力解析」出半截数据 | MediaCrawler 多条 issue 源于平台改版 |
| **⑧ 采集前先 preflight** | 开抓之前先探测：代理通不通、登录态在不在、目标接口响应结构是否变了 | 两个独立项目都自发演化出了这一步 |

**这条与机制 7 的关系**：机制 7 量化「数据够不够」，机制 9 保证「数据是不是真的」。**两者缺一不可** —— 一批全是假的完整数据，coverage 会算成高置信，比缺数据更糟。

## 七、开发前置规则（项目开始前必做）

### 7.0 铁律：先调研，再动手

**任何模块开工前，先查 GitHub 上有没有同类项目或可用工具，并验证其可用性与可靠性。结论写入 [docs/PRIOR-ART.md](PRIOR-ART.md)。**

三个必答问题：

1. **有人做过吗？** —— 避免重复造轮子（如研招网接口可达性、百度指数加密参数已有现成逆向）
2. **还能用吗？** —— 不只看 star 数，要看最后提交时间、issue 状态、核心假设是否仍成立
3. **许可证允许吗？** —— GPL / 非商业许可会直接约束代码复用（本项目已因此放弃复用 BaiduIndexHunter 代码）

**验证分档必须标注**，不许用「看起来不错」代替结论：

| 档位 | 含义 |
|------|------|
| ✅ 实读验证 | 实际读了代码/文档全文，可下确定结论 |
| ⚠️ 表层验证 | 只看了 README/目录，核心能力未实测 |
| ❌ 未验证 | 已知不可靠或已淘汰 |

**首轮调研已完成（2026-09-18）**，成果见 [docs/PRIOR-ART.md](docs/PRIOR-ART.md)。它对本项目的具体影响：

- 数据模型补齐 4 个字段（国家线 / 培养方式 / 学位类型 / 结构变化）
- 引入不确定性量化公式（coverage 阈值 0.75 / 0.45）
- 确立「缺失不是 0」「反方审查」「留出检查」「结论措辞纪律」四条硬性规则
- **新增工程约束：热度代理指标必须可插拔、可降级** —— 百度指数采集存在算法失效风险（依赖账号 Cookie + 加密参数逆向，7 个月未更新的项目已不可用），任何一个代理信号源挂掉不能影响主链路

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 爬虫被封 IP | 采集中断 | 严格限速（≥3s/请求）、UA 轮换、必要时换出口；优先抓静态 PDF |
| 数据口径错误 | **产生错误结论** | 口径归一 + 双人复核（你 + 规则引擎）+ 冲突标记 |
| 合规风险 | 法律问题 | 只抓公开数据、遵守 robots、不传播原文、注明来源 |
| 学校数据逐年变更 | 历史数据失真 | 保留历史快照，标注届次 |
| 热度模型过拟合 | 分数失真 | 指标可解释优先，不做黑盒；保留 score_version 便于回溯 |
| 单点 VM 故障 | 数据丢失 | 定期 dump MySQL + 快照；重要原始文件多副本 |
| **采集静默失效 → 假信号** | **给出错误结论（比缺数据更糟）** | **机制 9 全套**：空结果告警 + `fetched_count` + 历史基线比对 + 健康检查真探测 |
| **代理配置写了但没生效** | 以为在走代理，实际直连失败 | 启动时发真实请求验证出口 IP，不信任配置文件（见 PRIOR-ART.md §八） |
| **国内站点被误送进代理** | 抓 `.edu.cn` 绕道境外，慢且易失败 | 宿主机 `NO_PROXY` 不含 `.cn`；**显式控制**代理策略，国内直连、境外走代理 |
| **变更监听漏报附件变更** | ⚠️ **最隐蔽的漏报** | **招简/拟录取名单/专业目录大量是 PDF/Excel 附件**。只监听 HTML，附件换了 hash 也不变 → 必须下载附件并比对内容 |
| **变更监听误报（改版噪声）** | 告警疲劳，真告警被淹没 | 忽略规则（时间戳/访问计数/随机 token）；只对选择器定位的正文块做 diff |
| **报名期任务失败** | **窗口一年一次，无重试机会** | 报名期前 dry-run；失败即时告警到人；关键快照多副本留存 |
| **报名期高频扫描构成干扰** | 对方服务器正处峰值，加重负担/触发风控 | 逐日 1 次足够（学校播报不会更频繁）；守 robots、限速、不并发 |
