## 〇、为什么要做这件事

避免两种浪费：

1. **重复造轮子** —— 已经有人解决过的问题（如研招网接口可达性、百度指数加密参数）不值得再逆向一遍
2. **踩别人的坑** —— 有些方案看起来成熟，但其核心假设已经失效（如百度指数的 `ab_sr` 参数算法变更），依赖它等于给自己埋雷

**核心原则：不因为「有 star」就采用，也不因为「小众」就忽略。看的是①能不能用、②还能不能用、③许可证允不允许。**

### 2.1 ⭐ 最有价值：mcxiaoxiao/kaoyan-navigator-skill

| 项 | 内容 |
|----|------|

| 许可证 | **MIT** ✅ 可自由借鉴与复用 |
| 验证档位 | ✅ 实读验证（读了 SKILL.md / data-schema.md / decision-model.md / validate_data.py / LICENSE 全文） |

**它做了什么**：把择校判断当作「有证据约束的导航研究」，产出可审计的风险信号 + 证据质量 + 置信度。**和本项目的核心哲学完全一致**，甚至措辞都接近：

> 原文：「把择校判断当作有证据约束的导航研究，不承诺预测结果。」
> 原文：「缺失不是 0，标记为 `unknown`。」
> 原文：「'数据不足'不是'安全'。」

**可直接借鉴的 5 项具体成果**：

1. **八维风险模型（带权重，合计 100）**

   | 维度 | 高风险信号 | 权重 |
   |------|---|--:|
   | 分数洼地反弹 | 近两年复试线不高于国家线 10 分，且调剂/热度上升 | 15 |
   | 统考供给 | 统考名额同比下降 ≥25%，或连续下降 | 20 |
   | 小样本波动 | 统考名额 < 20（< 10 更高危） | 10 |
   | 推免挤压 | 推免占比累计上升 ≥10 个百分点 | 15 |
   | 竞争加剧 | 报录/复录比明显上升，或上线数超可录取数 | 15 |
   | 复试线虚低 | 录取中位数高于复试线 35 分，或最低分高 20 分 | 15 |
   | 结构变化 | 改考、专业拆并、学院调整、口径变化 | 15 |
   | 网络热度 | 「捡漏/闭眼冲/性价比」内容显著增加 | 5 |

   每维按 `0 / 0.5 / 1` × 权重打分。**注意它给「网络热度」只留了 5 分** —— 这与我们的 L4 只能做趋势的定位一致。

2. **不确定性惩罚的量化公式**（填补了我们设计的空白）

   ```
   coverage = 已有核心字段数 / 应有核心字段数
   核心字段 = 三年 × (复试线, 统考名额, 录取分布, 竞争数据) = 12 个单元

   coverage ≥ 0.75  → 高置信度
   0.45 ≤ coverage < 0.75 → 中置信度
   coverage < 0.45  → 低置信度
   ```
   附加约束：**只有 ≥2 个 A/B 级来源、且不存在未解决的对象混用，才能给「高置信度」**。

3. **反方审查（每个高风险结论必答 4 问）**
   - 是否由口径变化造成，而不是竞争真的增加？
   - 是否存在扩招、推免未满、复试保护一志愿等缓释证据？
   - 最近一年是否为疫情、政策或考试难度异常值？
   - 结论在删除最极端一年后是否仍成立？

4. **留出检查（防自欺）**：若有 4 年以上数据，用早期年份形成规则，再看最近一年能否被解释；**不得事后修改阈值冒充预测准确**。

5. **数据校验脚本** `scripts/validate_data.py`（可直接复用）：检查年份/学校/学院/专业/培养方式非空、数值非负、`(year, school, college, major_code, major_name, study_mode)` 唯一。**它允许字段为空** —— 只校验「非空字段是否合法」，不强迫填满，这与「缺失不是 0」一致。

**它的数据 schema 与我们的 `admission` 表对比**：

| 它的字段 | 我们的字段 | 差异 |
|---|---|---|
| `national_line` | —— | **我们没有，应补**（国家线是判断「分数洼地」的基准） |
| `retest_line` | `retest_line` | 一致 |
| `planned_total` | `plan_total` | 一致 |
| `recommended_exempt` | `plan_recommend` | 一致 |
| `unified_quota` | `plan_exam` | 一致 |
| `applicants` | `applied_count` | 一致 |
| `retest_count` | `retest_count` | 一致 |
| `admitted_count` | `admitted_count` | 一致 |
| `admitted_min` | `score_min` | 一致 |
| `admitted_median` | `score_median` | 一致 |
| `admitted_mean` | `score_avg` | 一致 |
| `study_mode` | —— | **我们没有，应补**（全日制/非全，口径归一的关键字段） |
| `degree_type` | —— | **我们没有，应补**（学硕/专硕） |
| `subject_change` | —— | **我们没有，应补**（改考 408 等结构变化信号） |

### 2.2 auroraso/BaiduIndexHunter（百度指数采集）

| 项 | 内容 |
|----|------|
| 地址 | https://github.com/auroraso/BaiduIndexHunter |
| 形态 | 前后端分离采集平台：Flask + Vue 3 + Element Plus + MySQL 8 + Redis 7.4 + Scrapy |
| 规模 | 14★ · 无 issue · 有测试目录 |
| 活跃度 | 最后提交 **2026-02-09**（约 7 个月前） |
| 许可证 | **自定义 EULA，非商业** ⚠️ **不可复用代码** |
| 验证档位 | ⚠️ 表层验证（读了 README 全文，未运行） |

**它做了什么**：百度指数六大维度（搜索指数/资讯指数/需求图谱/人群属性/兴趣分布/地域分布）采集，含 Cookie 池轮换、断点续爬、WebSocket 实时进度、六种格式导出。

**关键技术细节（重要）**：
- 逆向了对百度指数的 `Cipher-Text` 加密参数（`engine/crypto/Cipher-Text.js`）+ 维护 `ab_sr` Cookie（`ab_sr.js`）
- **必须提供已登录百度指数的账号 Cookie** 才能采集
- 有「Cookie 用量可视化 + 封禁预警」—— 说明封禁是常态化风险

**可靠性判断：⚠️ 不可作为依赖，只可作为参考**
1. **算法逆向具有时效性** —— 百度若变更加密参数，项目即失效。最后提交 7 个月前，**当前是否仍可用未知**
2. **依赖个人账号 Cookie** —— 封号风险由使用者承担，不适合作为长期自动化管道的一环
3. **许可证明确禁止商业使用** —— 本项目虽为自用，但代码复用会引入许可约束

**决策：借鉴架构，不采用代码；对百度指数保持「可降级」设计。**
具体做法：
- 热度代理指标必须**可插拔**：百度指数抓不到时，整体功能不能挂
- 优先考虑**不需要登录**的替代信号（B站/知乎搜索结果的公开计数、研招网报考人数等）
- 若确要采集百度指数，把它放在 Phase 2 之后的独立模块，且明确标注「来源 L4，仅供趋势」

## 六、调研结论：对本项目设计的具体影响

### 6.1 必须补进 DESIGN.md 的（来自 prior art 的增量）

1. **数据模型补 4 个字段**：`national_line`（国家线）、`study_mode`（全日制/非全）、`degree_type`（学硕/专硕）、`subject_change`（改考/结构变更）
2. **不确定性惩罚公式落地**：用 coverage 比例 + 阈值（0.75 / 0.45）作为置信度计算的一部分
3. **「缺失不是 0」写为硬性规则**：空值留空，`0` 只表示官方明确为零
4. **反方审查纳入指标流程**：每个高风险结论必须附一条可能降低风险的证据
5. **留出检查写为规则**：**不得事后调参冒充预测准确**
6. **结论措辞规范**：禁用「一定爆」「稳上」「准确率 X%」；使用「风险 / 情景 / 信号 / 置信度」
7. **「数据不足」不等于「安全」** —— 作为前端展示原则

### 6.2 维持我们原设计不变的（prior art 未覆盖或有差异）

| 我们的设计 | 状态 |
|---|---|
| 逐人分数明细表 `admission_detail` | ✅ 保持 —— prior art 无明细层，这是我们的核心增量 |
| 分位数（P25/P50/P75/P90） | ✅ 保持 —— prior art 只有 min/median/mean |
| 证据留存（原始 HTML/PDF 快照） | ✅ 保持 —— prior art 只存 URL，我们存快照，更强 |
| 四层来源分级 L1–L4 | ✅ 保持，但需与 prior art 的 A/B/C/D 建立映射表 |
| RabbitMQ 解耦采集与消费 | ✅ 保持 —— 无 prior art 涉及 |
| 时间衰减机制 | ✅ 保持 —— prior art 只做「三年趋势」，未量化衰减 |

### 6.3 新增的工程要求

1. **热度代理指标必须可插拔、可降级** —— 百度指数采集存在失效风险（见 2.2），任何一个代理指标挂了不能影响主链路
2. **优先选无登录依赖的信号源** —— 降低封号与合规风险
3. **Phase 0 增加一项验证任务**：实测研招网 `/sch/`、`/kyzx/zsjz/` 的可达性与抓取稳定性

### 7.4 全网搜索：SearXNG + 已有代理

**决定：用 SearXNG 自建全网搜索。** 34k★ 级同类方案 [changedetection.io](https://github.com/dgtlmoon/changedetection.io) 另见 §7.5。

#### ✅ 已部署（2026-09-18 实测完成）

| 项 | 值 |
|----|-----|
| 位置 | Kali 宿主机 `/opt/gradheat/searxng`（**非 Docker**，见下方出网决策） |
| 服务 | `systemd` 单元 `searxng`，enabled + active |
| 监听 | `127.0.0.1:8890`（避开被其他项目占用的 8888） |
| 配置 | `/opt/gradheat/searxng-config/settings.yml` |
| 版本要求 | `setup.py` 声明 `python_requires>=3.10`；VM 实测 **Python 3.13.11**，满足 |

**引擎实测结果**：

| 引擎 | 状态 | 说明 |
|------|------|------|
| `google cse` | ✅ 稳定（20 条/次） | 走官方 API，**不受代理 IP 风控影响 —— 主力** |
| `brave` | ✅ 可用（16~20 条/次） | 直接抓取 |
| `bing` | ✅ 可用（10 条） | 需显式 `engines=bing` 才进默认结果 |
| `google`（正牌） | ❌ `CAPTCHA` | 代理出口是数据中心 IP，被 Google 标记 |
| `duckduckgo` | ❌ `CAPTCHA` | 同上 |
| `baidu` | ❌ 302 → 验证页 | **与代理无关**：直连同样被挡（302，302→验证），需真实浏览器种下的 BAIDUID cookie |

**验收证据（真实返回）**：查询「西安电子科技大学 计算机 拟录取名单」→ **40 条结果**，直接命中
`scse.uestc.edu.cn/info/1015/16958.htm`「2025年计算机（网安）学院硕士研究生招生拟录取名单」、西电研究生院、电子科大研招网。
**检索能力可直接触达本项目核心数据源，已验证。**

**踩过的坑（供复用）**：

| 坑 | 现象 | 解法 |
|----|------|------|
| `search.formats` 默认只有 `html` | JSON API 返回 **403** | 加 `- json`（调研时预判，实测证实） |
| `searx` 包不在 venv 里 | `ModuleNotFoundError: No module named 'searx'` | 设 `PYTHONPATH=/opt/gradheat/searxng`（`pip install -e .` 因构建隔离缺 msgspec 而失败，不需要） |
| limiter 缺失告警 | `missing config file: limiter.toml` | 从 `searx/limiter.toml` 复制一份（limiter 仍为 false） |
| `duckduckgo`/`google` 不可用是**预期内** | 数据中心 IP 的必然待遇 | 用 `google cse` 替代 |

#### 出网决策：容器不走代理，出网任务跑宿主机

**用户决策（2026-09-18）**：`allow-lan: false` 且只听 `127.0.0.1` 的问题**不需要解决** —— 因为 **Docker 容器根本不需要代理**（只跑 MySQL/Redis/RabbitMQ 等内网服务）。需要出网的服务直接跑 Kali 宿主机，与 mihomo 同网络命名空间，`127.0.0.1:7890` 天然可达。

| 原方案 | 结论 |
|--------|------|
| ~~A. 开放 mihomo 到 Docker 网段~~ | ❌ 废弃 —— 不需要改 mihomo，不碰 VM 上其他项目在用的配置 |
| ~~B. `network_mode: host`~~ | ❌ 废弃 —— 不需要破坏容器端口隔离约定 |
| ~~C. `--add-host=host-gateway`~~ | ❌ 废弃 —— 同 A，多此一举 |
| **D. 出网任务跑宿主机** ✅ | **已实施**。零配置改动，风险最小 |

**⚠️ 原「未验证假设」现已实测证实成立**：mihomo 是 `mode: rule`，实测**国内域名确实被直连**：

```
经代理：百度 0.247s | 知乎 0.369s | B站 0.299s | tsinghua.edu.cn 0.846s | Google 1.58s(经隧道)
真直连：百度 0.493s | Google 15s 超时(不可达) | 出口 IP 经代理为 85.237.206.10
```

**`.edu.cn` 确实被规则集覆盖为直连** —— 这原本是我方标注的未验证假设，现已证实。因此**给 SearXNG 设全局代理是安全的**，路由交给 mihomo 规则引擎。

但仍**不依赖**该结论：规则集由订阅方维护、可能变动，故按机制 9 ⑪⑫ 显式控制代理并在启动时验证出口 IP。

**注意合规边界**：SearXNG 只应聚合**允许抓取的引擎**。Google/Bing 经代理抓取属个人自用研究范畴，但需严格限速，不做大规模抓取。

### 7.5 变更监听（`监听` 需求的正确形态）

用户提出「监听报名按钮 / 考研信息网页」的需求。**结论：流量监听不可行，变更监听可行且价值更高**（完整论证见 DESIGN.md §新增维度）。工程载体：

| 方案 | 说明 | 档位 |
|------|------|------|
| [changedetection.io](https://github.com/dgtlmoon/changedetection.io) | 34,319★，Python，2021 起持续维护，今日仍更新，自建 Web 服务，支持 CSS 选择器定位 + 通知 | ⚠️ 表层验证（未部署实测） |
| 自建 | httpx + 内容 hash + diff，轻量可控，与我们管道天然集成 | —— |

**初判：倾向自建**。理由：我们的场景需要「变更 → 触发数据管道入库」，而不是「变更 → 给人发通知」；changedetection.io 是给人用的监控台，与我们的自动化管道集成反而绕远。但若只做「招简发布提醒」这类运营功能，它开箱即用更省事。

## 八、Issue / PR 挖掘：真实世界的失效模式（2026-09-18）

> **为什么必须看 issue**：README 展示的是项目想让你看到的样子，**issue 才是它真实运行的记录**。
> 本次逐个读了 MediaCrawler（163 open）与 Agent-Reach（83 open）的近期 issue，挖到 10 类失效模式。
> **这些对我方的价值高于项目本身** —— 因为它们全部是我们采集管道未来必然会遇到的。

### 8.1 最高价值的一条：「抓到 0 条」被当成数据

**实例**：[last30days-skill-cn #11](https://github.com/Jesseovo/last30days-skill-cn/issues/11)（2026-07-18，仍 open）

小红书 `/api/sns/web/v1/search/notes` 接口废弃，新版页面改请求 `search/recommend`。
但该接口返回的是**搜索框下拉联想词（`sug_items`）**，payload 里**完全没有 `items`/`note_card`**：

```
[爬虫-小红书] 未捕获搜索 XHR，可能需要重新登录...
[xiaohongshu] 0 条结果        ← 爬虫"成功"结束，但一条没抓到
```

同一问题在 [#8](https://github.com/Jesseovo/last30days-skill-cn/issues/8) 被重复报告。

> **⚠️ 这个 bug 是本项目最危险的失效模式。**
> 如果我们的采集管道把「0 条」当作合法结果入库，前端就会显示
> **「某校 2026-03 小红书讨论量 = 0」** —— 看起来是**该校突然降温**，
> 实际上是**爬虫坏了**。这是「假的降温信号」，比没有数据危险得多。

**→ 落地为硬性规则**：

| 规则 | 说明 |
|------|------|
| **采集返回空/异常低值 → 告警 + 标记 `missing`，绝不入库为 0** | 与 DESIGN.md「缺失留空不填 0」同源，但这里有了真实世界的反面案例 |
| **解析结果条数必须与历史基线比对** | 如"上月抓到 200 条，本月 3 条" → 触发异常告警而非静默入库 |
| **每次采集必须记录 `fetched_count` 元数据** | 让「抓到多少」成为可审计的一等公民 |

### 8.2 十类失效模式汇总

| # | 失效模式 | 真实实例 | 我方对策 |
|---|---------|---------|---------|
| 1 | **空结果被当数据** | last30days #11/#8 | 见 8.1，入库前做条数合理性校验 |
| 2 | **自检假阳性**：健康检查说 OK 但实际不可用 | Agent-Reach #685（doctor 报 web channel ok，实际 Jina Reader 不可达）、#642（pin 的依赖被 WAF 403，doctor 覆盖不到） | 健康检查必须**发真实请求并校验响应内容**，不是只看 HTTP 200；检查要覆盖到依赖层 |
| 3 | **过期凭据静默屏蔽兜底**：既不用 A 也不走 B，静默失败 | Agent-Reach #664（过期 cookie 静默屏蔽了 fallback 路径） | 凭据失效必须**显式报错并触发降级**，禁止静默 |
| 4 | **配置写入成功但未生效** | Agent-Reach #702（cookie 写入后未被流程使用，提示与行为不一致） | 配置写入后必须**验证生效**再报成功 |
| 5 | **平台改版导致解析器失效** | MediaCrawler #871（百度贴吧网页版改版，HTML 解析全挂） | 解析器要能报「异常少量结果」；**改版即告警**（变更监听的价值之一） |
| 6 | **平台接口废弃** | last30days #11、MediaCrawler #914（微博 detail 失效）/#954（快手下载失效） | 多后端路由 + 每个后端独立健康探测 |
| 7 | **去重/截断污染指标** | MediaCrawler #907（微博关键词搜索**只返回去重后**的结果，拿不到全部） | 讨论量**只能同平台同口径比趋势**，不可横比；元数据记录口径 |
| 8 | **封号是真实发生的** | MediaCrawler #915（只是查看帖子+下载视频，被小红书提示"检测到 AI 操作"，9 条讨论） | 只采集公开聚合计数；用小号；严格限速；不做内容大规模抓取 |
| 9 | **供应链/归属风险** | Agent-Reach #658（doctor 引导用户装**非官方的** Chrome 扩展） | 不引导安装来源不明的扩展/二进制 |
| 10 | **环境硬约束未预先声明** | last30days #13（Playwright 浏览器二进制要求 macOS 13.5+） | Phase 0 先实测 Kali 上 Playwright 的浏览器依赖 |

### 8.3 从 issue 里捡到的两条直接可用的情报

**① Exa 可直连 REST，不必走 MCP**
[Agent-Reach #646](https://github.com/Panniantong/Agent-Reach/issues/646)：有 API Key 时直连 Exa REST，保留 MCP 回退。
→ **我方已配置 Exa API Key**（在 `.claude/settings.local.json`）。**采集脚本应直连 REST**；MCP 是给交互式 agent 用的，不适合无人值守的定时管道。

**② 「采集前预检」是共性刚需**
[MediaCrawler #960](https://github.com/NanmiCoder/MediaCrawler/issues/960)：用户主动提 issue 要求「Add a lightweight preflight check for cookies/proxy before starting a crawl」。
→ 与 Agent-Reach 的 `doctor` 设计殊途同归。**两个独立项目都演化出同一个需求，说明这是刚需，不是过度设计。**
→ 我方采集器开工前必须自检：代理通不通、目标站点是否仍可达、解析器是否还能解析出合理条数。

### 8.4 结论：`doctor` 设计要抄，但必须修掉它的 bug

Agent-Reach 的「多后端路由 + doctor 自检」范式值得照搬，**但它的 issue 说明这个范式有两个必须避开的坑**：

```
❌ 它的问题：doctor 只检查"命令存不存在" → 假阳性（#685）
             检查不到依赖层的失效（#642）

✅ 我方的做法：每个 channel 健康检查 = 发一次真实请求 + 校验响应结构符合预期
             检查结果分三态：healthy / degraded(走了备选后端) / down
             down 时管道降级运行并显式标注该维度数据缺失，绝不静默
```

## 九、报名期数据可得性核实（2026-09-18）

> **起因**：用户提问「能否在报考时间段抓取报考网站的流量、或流量的报考学校」。
> 这不是工具选型问题，而是**数据是否存在于公开世界**的问题，故单列一节核实。

### 9.1 核实结论：流量路线不可行，且原因是制度设计

| 想要的信号 | 结论 | 依据 |
|-----------|------|------|
| 研招网站点流量 | ❌ 不可得 | 站点无公开计数器；第三方估算只到 `chsi.com.cn` 域名级，无法拆分到学校 |
| 各校报名人数**实时分布** | ❌ 不可得 | 网报系统为**登录态、每人只见自己的填报**；研招网**不提供**任何实时报考人数查询 |
| 研招网页面「关注人数/热度」 | ❌ 不存在 | 已核实官方[硕士专业目录](https://yz.chsi.com.cn/zsml/)只有招生单位、院系所、专业、学习方式、研究方向、拟招生人数、指导教师、考试科目等硬信息，**无热度类字段** |

**关键判断：这是制度设计，不是技术疏漏。** 若考生能实时看到各校报名人数，会立即引发扎堆/规避博弈，报名秩序被打乱。教育部刻意不公开。

> **→ 由此确立一条排除规则**：**不接受任何第三方估算值，也不用「准考证号推算」等民间方法** —— 前者只到域名级（对 `.edu.cn` 基本是噪声），后者已核实「并不精准」，两者都过不了来源分级。

### 9.2 但存在一个真正的增量：报名期公布的报名进度

**部分学校在报名窗口未关闭时即主动公布报名人数**，实测案例：

| 学校 | 公布时点 | 数据 | 来源 |
|------|---------|------|------|
| 北京航空航天大学 | 2024-10-23 | 12,714 人，同比 -7%，连续第三年下降 | [25考研报考人数最新公布](https://mp.weixin.qq.com/s?__biz=MzIzNjE3NDgxMA==&mid=2652344374&idx=2&sn=6f4e3b4ce4bdbe98460ffeffabfae73c) |
| 沈阳药科大学 | 2024-10-23 | 3,196 人，同比 -31% | 同上 |
| 西安财经大学 | 2024-10-28 | 4,691 人，同比 -25% | 同上 |

**这是报名期内唯一可得的真实报考数据**，已立项为 DESIGN.md §1.5「报名期进度快照」，由报名期专项变更监听任务（复用 §7.5 设施）采集。

⚠️ **覆盖率低是硬约束** —— 是否公布完全自愿。未公布即 `missing`，不用代理指标补估算。

### 9.3 三层替代数据（均不做院校排名）

| 层级 | 数据 | 粒度 | 用途 |
|------|------|------|------|
| 全国 | 2025 年 **388 万**，同比 **-11.4%**（教育部） | 全国 | 大盘归一基准 |
| 省级 | 山东 35.5万 / 江苏 25.2万 / 广东 21.26万（各省考试院） | 省 | 区域热度背景 |
| 报考点 | 各省考试院「**已满报考点实时更新公告**」，部分考点临时扩容（3,000→3,500） | 考点 | ⚠️ **只能做省级总量背景** |

### 9.4 解读纪律（数据能拿到 ≠ 能直接用）

| 陷阱 | 说明 |
|------|------|
| **公布 ≠ 热度** | 不能用「学校是否公布」作为热度指标 —— 那测的是**学校的宣传意愿**。北大从不公布，不代表北大冷 |
| **公布带动机** | 有的公布低数字吸引考生（捡漏宣传），有的公布高数字劝退（分流宣传）。须过机制 8 反方审查 |
| **同比口径不明** | 「同比下降 31%」对比的是去年**哪个时点**？若拿「今年第 5 天」比「去年最终数」，这个百分比是假的 → **存学校原文，不存加工值**（机制 5） |
| **滚动值 ≠ 最终值** | 报名期数据含取消报名、重复报名、网上确认未通过者。必须标注「**未经网上确认**」 |
| **时点不可比** | 不同学校公布时点不同 → 跨校比较必须对齐时点 |

## 十、本文档的维护规则

- **新模块开工前**：先在本文件追加一节，写明「调研了什么 → 验证结论 → 采用/借鉴/弃用 + 理由」，然后再写代码
